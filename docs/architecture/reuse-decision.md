# ADR: переиспользование платформ и границы backend

Статус: принято для основы JanaMen. Дата: 17.10.2026.

Подробные первичные источники, версии и ограничения: [исследование backend](../research/backend-rea.md).

## Контекст и критерии

JanaMen объединяет профиль сотрудника, кадровые заявки, обучение, знания и уведомления. Официальные кадровые факты остаются в 1С. Documentolog остаётся внешней системой документооборота. Для хакатона используются синтетические данные и рабочие mock-адаптеры.

Пользователь выбрал полноту и качество: около 30 разных курсов, отпуск и аванс, несколько команд, разные состояния записей, рабочий HR-контур, доказательная база AI. Срок хакатона не используется как довод для урезания этого объёма.

Критерии выбора: корректность модели владения данными; единый доступ для всех модулей; надёжность переходов; отсутствие дублирующих источников истины; переиспользование зрелой инфраструктуры; свобода отдельного frontend; возможность объяснить и проверить систему. Количество файлов и скорость первого запуска не являются самостоятельной целью.

## Решение

Один модульный backend на **Django + Django REST Framework**, основная база **PostgreSQL**, готовые административные возможности Django для управления содержимым, версионированный REST API и генерируемая схема OpenAPI. Frontend реализуется отдельно и получает контракт из backend.

Полномочия, переходы и эффекты выполняются в сервисах предметных модулей. Модели не публикуются клиенту как неограниченный CRUD. Django admin не подменяет будущий продуктовый интерфейс сотрудника и руководителя.

## Сравнение архитектур

| Вариант | Что получаем готовым | Что всё равно придётся сделать | Ключевой компромисс |
|---|---|---|---|
| Frappe HR + ERPNext + Learning | Обширные HR и LMS-модели, документы, регистры, админка, API | Согласование с 1С, иной смысл аванса, единый UX, RAG, настройка прав, adapters | Высокое переиспользование предметного кода, но ERP становится вторым владельцем кадровых/финансовых фактов. |
| Payload + Next.js + PostgreSQL | Auth, контентные коллекции, поля, админка, локализация, REST | HR workflow, команды, правила, результаты LMS, атомарные эффекты | Сильный вариант для общего TypeScript и контентного продукта; наш core не сводится к редактированию документов. |
| Django + DRF + PostgreSQL | Auth, сессии, CSRF, ORM, транзакции, миграции, admin, API primitives | Узкий набор правил JanaMen, object scopes, обучения и integrations | Выбран: один явный transactional domain, независимый frontend и нет второго кадрового ядра. |
| Отдельный Moodle + HR backend | Готовый учебный движок, административное обучение, web services | Связь пользователей, прав, назначений, результатов и общий API/UX | Уместно, если принимаем его модель обучения; требует честно выбрать единственного владельца результата. |
| Supabase + frontend/server functions | PostgreSQL, auth, storage, RLS | HR/LMS domain, согласование транзакций, публикация и admin | Сильный infrastructure-вариант; не заменяет предметный backend и не нужен вторым Auth. |

У Frappe есть совместимый стабильный диапазон версий; его не отклоняли из-за ветки `develop`. У Payload есть транзакции и granular access; его не отклоняли из-за невозможности защищённого backend. Выбор основан на том, какой слой мы строим над существующими системами Jana Post.

## Владение данными

## Два структурных эскиза до реализации

Pstack architect требует сравнить разные формы системы. До реализации рассмотрены следующие варианты.

**Эскиз A. Полный Frappe.** Один Frappe site содержит ERPNext, HR и Learning. JanaMen frontend вызывает Frappe REST; отдельное приложение расширения выполняет `submit_leave(employee, dates)` и `assign_course(employee, course)`. 1С синхронизируется в ERPNext Employee и отпускной регистр. Сложность HR/LMS скрывается внутри готовых DocType, но требуется определить, какая система имеет последнее слово при изменении кадрового факта и финансовой операции.

**Эскиз B. Модули JanaMen на Django.** Один Django application содержит identity, requests, academy, knowledge, notifications и integrations. Frontend вызывает версионированный API. Сервис `submit_request(actor, request_id, expected_version, idempotency_key)` выполняет одну атомарную команду. Сервис `assign_learning(actor, employee, course_version)` обращается к общей модели сотрудников и событий. 1С импортирует read-only снимок, Documentolog получает outbox-команду. Сложность авторизации и транзакций скрыта в небольших общих интерфейсах; предметная модель ограничена ответственностью портала.

**Эскиз C. Payload как прикладное ядро.** Next.js route handlers вызывают guarded Local API с пользовательским контекстом; коллекции хранят сотрудников, заявки и обучение, hooks выполняют бизнес-переходы и outbox. Админка и контент хорошо переиспользуются, но все transactional команды и командные полномочия всё равно требуют собственного слоя. Передача `req` и запрет bypass должны быть конструктивно обеспечены обёрткой.

Выбран эскиз B. Он сохраняет кадровое владение у 1С, даёт независимому frontend стабильный контракт и не превращает бизнес-команды в неограниченные обновления коллекций. Pstack Model the Domain повлиял на решение хранить состояния, ревизии и события явно, а Type System Discipline требует получать frontend-типы из OpenAPI. Это архитектурное сравнение по исходникам и контракту; замер быстродействия трёх запущенных систем не проводился.

| Факт | Владелец | Как используется в JanaMen |
|---|---|---|
| Должность, юрлицо, отдел, руководитель, дата трудоустройства | 1С/mock 1С | Импортированный read-only профиль с временем синхронизации. |
| Официальный отпускной остаток | 1С/mock 1С | Отдельное значение; не переписывается одобрением локальной заявки. |

## Границы модулей

### Identity и Organization

User, employee profile, legal entity, department, manager relationship, HR scope. User и Employee различаются: учётная запись управляет входом, кадровый профиль — данными сотрудника. Обычный manager работает с разрешённой командой; HR получает явную область организации. Менеджер не наследует все административные права.

Общие инварианты: активная сессия; автор команды определяется сервером; чужие данные не выдаются через список, карточку, поиск, экспорт, вложение или вложенные поля; кадровый импорт редактируется только интеграционной операцией.

### Requests

Request с общими данными маршрута; LeaveDetails и AdvanceDetails с разными полями и валидацией; immutable history; approval commands; reservations; integration references. Конкретный набор статусов фиксируется в спецификации API и реализации, а не выводится из свободной строки.

Инварианты:

- даты отпуска упорядочены, пересечения и доступный резерв проверяются сервером;
- деньги передаются десятичным значением и валютой, не `float`;
- заявитель не согласует себе заявку;
- принять решение может только назначенный и всё ещё уполномоченный согласующий;
- команды проверяют текущую версию/состояние; повторный клик не повторяет эффект;
- после отправки значимые условия не меняются незаметным редактированием;
- статус, история, уведомление/outbox создаются атомарно;
- решение руководителя и завершение внешней обработки отображаются отдельно.

### Academy

Course, immutable published CourseRevision, ordered lessons, quiz questions/options, Enrollment, LessonCompletion, QuizAttempt. Назначение курса отделено от опубликованного каталога. Архитектура поддерживает разнообразие 30 курсов, а не только единственный тестовый маршрут.

Инварианты:

- учащийся видит опубликованный и разрешённый контент;
- курс, employee и revision назначения не подменяются через update;
- процент вычисляется по фактам прохождения;
- правильные ответы и внутренние поля оценки не выдаются до разрешённого этапа;
- вариант ответа обязан относиться к вопросу и попытке;
- старт/сдача попытки проверяют принадлежность и лимиты;
- итог рассчитывается на сервере; уже сданная попытка сохраняет результат;
- повторный запрос завершения урока идемпотентен;
- завершение и его событие создаются один раз;
- обновление курса не меняет прошлый диплом/результат без явного нового назначения.

### Knowledge и AI Jana

Document, DocumentRevision, audience, chunks, retrieval request, cited answer, feedback/escalation. Индекс строится только по опубликованным и разрешённым источникам. AI использует разрешённый контекст, не принимает кадровые решения и не меняет регламенты от имени сотрудника.

Инварианты: фильтрация до retrieval/context; ссылки на реальные извлечённые fragment IDs; проверяемая ревизия источника; корректное отсутствие ответа; защищённая карточка/файл источника; отсутствие доступа к закрытым данным через embeddings или логи.

### Notifications и Integrations

Notification принадлежит получателю и ссылается на разрешённый ресурс. Outbox хранит подготовленные эффекты; worker доставляет их с повторными попытками и ключом дедупликации. Command receipt показывает внешнюю обработку отдельно от бизнес-решения.

Инварианты: получатель задаётся сервером; повторная доставка не создаёт дубль; failure не исчезает молча; внешний callback аутентифицирован и идемпотентен; mock и реальный адаптер используют один смысл контрактов.

## Что не пишем самостоятельно

Не разрабатываем свой password hashing, session store, ORM, migration engine, JSON serializer, HTTP server, full-text ranking algorithm, OpenAPI renderer или framework административных форм. Выбранные библиотеки фиксируются в зависимостях, а принятые меры безопасности проверяются тестами с реальными запросами.

При необходимости более сложного редактора курса, внешнего LMS или корпоративного SSO сначала выбирается зрелая реализация и адаптер. Наличие будущего адаптера в диаграмме не означает, что подключение уже работает.

## Последствия и проверка решения

Backend-команде потребуется поддерживать Python, frontend-команде — TypeScript. Общая схема API компенсирует отсутствие одного языка. В сравнении с Frappe мы пишем больше предметной логики портала, зато не принимаем ненужную ответственность за ERP-учёт. В сравнении с Payload получаем привычную явную транзакционную модель ценой отдельного frontend runtime.

Решение считается полезным только после проверки целых сценариев: сотрудник → заявка → руководитель → результат → уведомление; назначение → уроки → тест → профиль; вопрос → разрешённый источник → ответ/воздержание. Отдельно проверяются чужая команда, поддельные результаты, повторные команды, устаревшие версии, отмены, ошибки интеграции и сохранение истории.

## Когда пересмотреть ADR

Пересмотреть при появлении реального требования заменить 1С, принять Frappe как system of record, использовать стандартизованные учебные пакеты/массовую LMS-миграцию, поддержать отдельный коммерческий LMS-провайдер или объединить всю команду на одном TypeScript-стеке. Увеличение количества курсов с 30 до 300 само по себе не меняет границы владения данными.
