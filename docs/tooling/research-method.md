# Evidence in JanaMen research

Every product finding identifies its source, scope, and evidence type.

| Evidence type | What it can establish | What remains unknown |
| --- | --- | --- |
| Official product documentation | The vendor's documented behavior and terminology | Whether a particular account or deployed version behaves identically |
| Original source at a pinned revision | Implemented data shapes, algorithms, checks, and code relationships | Runtime configuration, deployed version, or visual behavior without execution |
| REA static shipped-artifact analysis | Captured modules, imports, route candidates, and evidence locations | Whether candidates executed or match server-side behavior |
| REA browser capture | Observed page structure, declared actions, accessible content, screenshots, and captured events | Unvisited states and private backend implementation |
| Documentation mirror capture | Structure of an identified downloaded artifact | Live service behavior and authenticated product workflows |
| JanaMen design decision | The selected adaptation and its acceptance criteria | Whether the future implementation passes those criteria |

Record the question before choosing a tool. Prefer a direct official source or complete source repository for a question those sources can answer. REA's skill explicitly excludes ordinary complete-source architecture analysis.

For a REA investigation, record the target URL or artifact path, capture date, digest, declared actions, Evidence IDs, exclusions, and unresolved questions. Preserve failures as failures. Do not infer success from a tool's presence or a screenshot filename.

A competitor pattern enters JanaMen only with a concrete purpose and an acceptance check. The adaptation must fit the real employee, manager, and HR contracts. Preserve source licenses for reused code. Use original JanaMen content and branding for the final product.
